## Introduction

과학 프로그램은 대개 일련의 계산 작업으로 시작한다. 데이터를 준비하고, 수학적 모델을 적용하고, 반복해서 상태를 갱신하며, 결과를 확인한다. 그러나 계산 결과가 한 번 올바르게 나왔다는 이유만으로 프로그램이 잘 구성되었다고 말할 수는 없다. 다른 연구자가 같은 계산을 재현하려면 초기조건, 단위, 계산 순서 및 오류 처리 방식까지 이해할 수 있어야 한다.

절차적 프로그래밍(Procedural Programming)은 명령문을 일정한 순서로 실행하고 관련 작업을 단계별로 조직하는 접근 방식이다. 이번 장은 `for`, `if` 등의 문법을 새로 배우는 장이 아니다. 알고 있는 Python 문법을 이용하여 **과학적 의미가 드러나는 절차적 계산 흐름**을 만드는 연습이다.

대표 사례는 일차원 입자 운동(P1)이다. 초기 위치, 속도, 일정한 가속도가 주어졌을 때 여러 시점의 상태를 계산한다. 이 예제에서는 물리 모델과 수치 계산 방법, 이전 상태와 갱신 상태, 현재 상태와 계산 이력, 실행 성공과 수치 정확성을 구분한다. 계산의 독립적인 함수화는 Chapter 4로, 상태의 객체화는 Chapter 6으로 남겨 둔다.

## 3.1 절차적 프로그램의 구성

### 3.1.1 명령과 실행 순서

명령형 프로그램은 명령의 실행 순서와 상태 변화에 의존한다. 단순한 등속 운동에서는 위치를 다음과 같이 계산한다.

$$x(t)=x_0+vt$$

```python
initial_position = 0.0
velocity = 2.0
time = 5.0
position = initial_position + velocity * time
print(position)  # 10.0
```

여러 시점에서 계산해야 한다면 `times = [0.0, 1.0, 2.0, 3.0]`을 순회하여 `[0.0, 2.0, 4.0, 6.0]`을 얻을 수 있다. 그러나 가속도가 존재하면 **상태를 갱신하는 순서가 수치 계산 방법 그 자체**가 된다. 명시적 오일러 방법은 다음 관계를 사용한다.

$$x_{n+1}=x_n+v_n\Delta t$$

$$v_{n+1}=v_n+a\Delta t$$

두 다음 상태는 모두 이전 시점의 값을 이용해야 한다. 초기 상태가 $x_0=v_0=0$, 가속도 $a=2$, 시간 간격 $\Delta t=1$이면 명시적 오일러의 첫 위치는 0이고 다음 속도는 2이다.

```python
position, velocity = 0.0, 0.0
acceleration, time_step = 2.0, 1.0
next_position = position + velocity * time_step
next_velocity = velocity + acceleration * time_step
position, velocity = next_position, next_velocity
print(position, velocity)  # 0.0 2.0
```

반대로 속도를 먼저 갱신한 후 그 속도로 위치를 계산하면 첫 위치가 2가 된다. 이는 반암시적 오일러(Semi-Implicit Euler), 즉 Euler–Cromer의 갱신 순서이다. 두 구현이 모두 실행되어도 **서로 다른 수치 방법**이므로 결과가 다를 수 있다. 코드를 정리할 때 연산의 순서를 무심코 바꾸어서는 안 된다.

### 3.1.2 변수와 상태 변화

변수의 재할당과 객체 내부 변경은 서로 다른 현상이다. `position = position + 2.0`은 이름에 새 값을 할당한다. 반면 NumPy 배열의 `positions[1] = 3.0`은 배열의 내용 자체를 변경한다. 원시 측정 데이터나 여러 계산 단계에서 공유되는 배열은 변경 여부를 명확히 해야 한다.

계산 시점이 중요한 문제에서는 `current_position`, `next_position`처럼 **현재 상태와 다음 상태를 구분하는 이름**을 사용하는 편이 안전하다. 한편 모든 변수를 무조건 길게 명명할 필요는 없다. 짧은 수학적 수식에서는 `x`, `v`, `a`, `dt`가 명확할 수 있다. 이름의 목적은 길이를 늘리는 것이 아니라 데이터의 의미와 생명주기를 드러내는 것이다.

현재 상태는 다음 단계의 입력이고, 계산 이력은 검증과 분석을 위한 기록이다. `position`, `velocity`와 `positions`, `velocities`를 혼동하지 않아야 한다. 상태가 변경된 시점과 기록된 시점도 맞아야 한다.

### 3.1.3 입력·처리·출력의 구조

입력·처리·출력(Input–Process–Output)은 과학 스크립트를 이해하기 위한 기본 틀이다. 입력에는 초기 위치·속도·시간 값이, 처리에는 운동 방정식과 수치 방법이, 출력에는 시간별 위치·속도 결과가 해당한다.

```python
# Input: SI units (m, m/s, s)
initial_position = 0.0
velocity = 2.0
times = [0.0, 1.0, 2.0, 3.0]

# Process
positions = []
for time in times:
    positions.append(initial_position + velocity * time)

# Output
print(positions)  # [0.0, 2.0, 4.0, 6.0]
```

작업 영역에 주석을 붙였다는 것만으로 관심사가 분리되는 것은 아니다. 각 단계의 입력과 출력, 데이터가 수정되는 위치, 계산 실패 조건이 분명해야 한다. 이후 함수로 분리하기에 앞서 절차 자체를 정확하게 이해하는 것이 중요하다.

## 3.2 계산 과정의 구조화

### 3.2.1 과학적 문제의 단계별 분해

과학 문제의 구현은 물리량·단위 정의 → 수학적 모델 설정 → 수치 방법 선택 → 초기조건 준비 → 상태 초기화 → 반복 계산 → 결과 기록 → 검증의 순서로 조직할 수 있다. 이번 실습의 기본 모델은

$$\frac{dx}{dt}=v,\qquad\frac{dv}{dt}=a$$

이며, 가속도는 상수이다. 초기조건과 계산 설정을 $x_0=v_0=0$, $a=2\,\mathrm{m/s^2}$, $\Delta t=1\,\mathrm{s}$, $N=4$로 놓고 명시적 오일러를 적용하면 시각 `[0,1,2,3,4]`, 위치 `[0,0,2,6,12]`, 속도 `[0,2,4,6,8]`을 얻는다. 초기 시점을 포함했으므로 네 단계의 계산으로 다섯 시점을 기록한다.

일정한 가속도의 정확한 위치는 다음과 같다.

$$x(t)=x_0+v_0t+\frac12at^2$$

따라서 4초에서 정확한 위치는 16m이다. 수치 계산 결과 12m와의 차이는 오류가 있는 Python 문법 때문이 아니라 유한한 간격에서 생기는 **수치 근사 오차**이다. 실행 성공, 구조적 일관성, 과학적 정확성을 구분한다.

### 3.2.2 반복 계산과 조건 분기

반복 계산을 설계할 때에는 초기 상태, 한 단계의 상태 갱신, 종료 조건을 구분한다. 고정 시간 구간에는 `for step_index in range(number_of_steps)`가 적절하다. 특정 위치 도달처럼 조건 자체가 종료 기준이면 `while`을 사용할 수 있으나, 도달 불가능한 조건을 대비해 최대 반복 횟수 같은 보호 장치가 필요하다.

```python
position, velocity, time = 0.0, 2.0, 0.0
time_step, target_position, max_steps = 1.0, 5.0, 100
step_index = 0
while position < target_position and step_index < max_steps:
    position += velocity * time_step
    time += time_step
    step_index += 1
print(time, position)  # 3.0 6.0
```

이 출력은 목표 위치 5m를 처음 **검출한 이산 계산 시각**이다. 정확한 도달 시각은 $5/2=2.5\,\mathrm{s}$로 다르다. 따라서 종료 조건 구현은 과학적 사건(Event)을 언제, 어떤 해상도로 인식할지에 관한 문제이다. 입자 상태에 `NaN`이나 무한대가 발생할 가능성이 있다면 `math.isfinite`로 유한성을 검사할 수 있지만, 유한한 결과가 곧 물리적으로 타당한 결과는 아니다.

### 3.2.3 중간 결과와 계산 흐름 관리

`position`과 `velocity`는 현재 상태이고 `positions`와 `velocities`는 계산 이력이다. 이력을 저장하면 각 시점의 결과를 검토하고 오류를 추적할 수 있다. 시간 기록을 포함해 `len(times) == len(positions) == len(velocities)`인지 확인하는 것은 기본적인 구조 검사이다. 다만 길이가 같아도 기록 시각과 데이터가 서로 어긋날 수 있으므로 상태를 갱신한 뒤 같은 시점의 결과를 일관되게 추가해야 한다.

일정한 양의 가속도와 비음수 초기 속도에서는 기록된 속도가 감소하지 않는지도 검사할 수 있다. 이것은 해당 조건에만 적용되는 **모델 기반 검증**이며, 모든 운동 문제의 일반적인 불변식은 아니다.

모든 중간 결과를 저장하는 데에는 메모리 비용이 따른다. 대규모 입자 집합이나 긴 시계열에서는 저장 간격을 조절하거나 필요한 집계값만 보존하는 방법을 고려한다. Chapter 3은 이러한 결정을 내리기 위한 개념을 제시하며, 성능 최적화 자체는 이후 장에서 다룬다.

## 3.3 읽기 쉬운 스크립트 설계

### 3.3.1 관심사의 분리

관심사의 분리(Separation of Concerns)는 입력 준비, 입력 검증, 수치 계산, 결과 검증, 결과 출력 등 서로 다른 책임을 구별하는 원칙이다. 하나의 스크립트 안에서도 섹션을 나누어 의도를 명확하게 만들 수 있다. 함수나 클래스를 도입하기 전에 **어떤 작업을 왜 구별해야 하는지**를 이해하는 것이 우선이다.

물리적 모델과 수치 방법 역시 서로 다른 관심사다. 모델 $dx/dt=v,\,dv/dt=a$는 연속시간의 물리 관계이고, 오일러 갱신식은 이를 컴퓨터에서 근사하는 방법이다. 모델에 문제가 있는지, 수치 근사에 문제가 있는지 구별하려면 이 차이를 유지해야 한다.

### 3.3.2 변수와 계산 단계의 명명

`x, v, a, dt`는 수학식과 밀접한 짧은 문맥에서 적절하다. 반면 스크립트의 설정·상태 관리 영역에서는 `initial_position`, `current_velocity`, `time_step`, `step_index`처럼 구분이 드러나는 이름을 사용한다. 특히 `step`이 시간 간격인지 반복 번호인지 혼동하지 않도록 한다.

단위가 섞일 위험이 있으면 `time_seconds`, `velocity_m_per_s`와 같이 단위를 이름에 반영할 수 있다. 하지만 이름 자체가 단위 검증을 수행하는 것은 아니다. 단위는 문서와 입력 계약에 명시해야 한다. 주석은 `position += 1` 같은 코드를 다시 읽어주기보다 **왜 이전 속도로 위치를 계산하는지**, **왜 특정 오차를 허용하는지**를 설명해야 한다.

### 3.3.3 오류 처리와 실행 흐름

이번 프로그램은 양의 시간 간격과 음수가 아닌 전체 계산 시간을 요구한다. 이는 모든 과학계산에서 역방향 시간이 금지되기 때문이 아니라 **여기서 다루는 계산의 계약**이 그러하기 때문이다. 입력값에 대해 `math.isfinite`, 범위 검사, 전체 시간과 간격의 정수배 관계를 확인한다.

오류가 발생하면 무조건 복구하려 하지 않는다. 특히 `except Exception: print('Calculation failed')`처럼 넓게 예외를 포착해 정상 종료처럼 보이게 만드는 코드는 문제를 감출 수 있다. 복구 가능한 I/O 오류와 계산 자체가 불가능한 매개변수 오류는 구분해야 한다. 오류 조건과 허용 범위는 이후 Chapter 9의 계약과 자동화된 검증에서 더욱 체계화한다.

## 3.4 실습: 입자 운동 계산

### 3.4.1 문제 정의와 물리량

P1 예제는 상수 가속도를 갖는 일차원 입자 운동이다. 위치는 m, 속도는 m/s, 가속도는 m/s², 시간은 s 단위를 사용한다. 초기조건 $x(0)=v(0)=0$, 가속도 $a=2.0$, 전체 시간 $T=2.0$, 시간 간격 $\Delta t=0.5$로 정한다. 총 계산 단계는 $N=T/\Delta t=4$이며 처음 상태를 포함해 다섯 기록을 생성한다.

정확한 해는 다음과 같다.

$$v(t)=v_0+at$$

$$x(t)=x_0+v_0t+\frac12at^2$$

따라서 $t=2$초에서 정확한 속도는 4m/s, 위치는 4m이다. 아래 구현은 의도적으로 독립 함수와 클래스를 사용하지 않고 **절차적 흐름을 명확히 보여주는 단일 파일**로 유지한다.

### 3.4.2 시간에 따른 위치·속도 계산

다음은 실습의 핵심 상태 갱신 부분이다. 실행 가능한 **전체 프로그램**은 함께 제공하는 `P1_particle_motion.py` 파일에 있으며, 입력 검증·기록·출력·정확한 해와의 비교까지 포함한다.

```python
# A standalone excerpt from the complete P1 program
position, velocity = 0.0, 0.0
acceleration, time_step = 2.0, 0.5
number_of_steps = 4
times, positions, velocities = [0.0], [position], [velocity]
for step_index in range(number_of_steps):
    next_position = position + velocity * time_step
    next_velocity = velocity + acceleration * time_step
    position, velocity = next_position, next_velocity
    times.append((step_index + 1) * time_step)
    positions.append(position)
    velocities.append(velocity)
print(positions)
print(velocities)
```

예상 출력:

```text
[0.0, 0.0, 0.5, 1.5, 3.0]
[0.0, 1.0, 2.0, 3.0, 4.0]
```

전체 프로그램의 결과는 다음과 같다.

| 시간 (s) | 수치 위치 (m) | 정확한 위치 (m) | 수치 속도 (m/s) |
|---:|---:|---:|---:|
| 0.0 | 0.00 | 0.00 | 0.0 |
| 0.5 | 0.00 | 0.25 | 1.0 |
| 1.0 | 0.50 | 1.00 | 2.0 |
| 1.5 | 1.50 | 2.25 | 3.0 |
| 2.0 | 3.00 | 4.00 | 4.0 |

명시적 오일러 방법은 이번 상수 가속도 조건에서 시각별 속도는 정확하게 계산하지만 위치에는 근사 오차가 존재한다. 끝 시점에서 수치 위치는 3m, 정확한 위치는 4m, 위치의 절대오차는 1m이다.

시간 간격을 줄이면 오차가 어떻게 변하는지 도출할 수 있다.

$$x_N=\frac12a\Delta t^2N(N-1)=\frac12a(T^2-T\Delta t)$$

$$\left|x_{\mathrm{exact}}(T)-x_N\right|=\frac12aT\Delta t$$

| 시간 간격 (s) | 단계 수 | 수치 위치 (m) | 절대오차 (m) |
|---:|---:|---:|---:|
| 1.00 | 2 | 2.00 | 2.00 |
| 0.50 | 4 | 3.00 | 1.00 |
| 0.25 | 8 | 3.50 | 0.50 |
| 0.10 | 20 | 3.80 | 0.20 |

이 사례에서 오차는 시간 간격에 비례한다. 시간 간격을 줄이면 계산 횟수가 늘어난다는 비용도 함께 고려해야 한다. 위 관계를 모든 운동 방정식이나 모든 수치 방법에 일반화해서는 안 된다.

### 3.4.3 절차적 프로그램의 개선

이 실습을 개선할 때에는 계산 조건을 스크립트 앞부분에 모으고, **이전 상태로부터 두 다음 상태를 모두 계산한 후** 상태를 갱신하며, 이력을 같은 시점에 기록해야 한다. 입력 검증, 기록 길이 확인, 유한값 확인 및 기준해 비교는 서로 다른 목적을 갖는다.

입력 조건 검사는 계산이 허용되는지 판단한다. 구조 검사는 시각과 상태의 기록이 서로 맞는지 확인한다. 수치 검사는 계산이 정확한 해나 신뢰 가능한 기준에 어느 정도 근접하는지 평가한다. 각 검사를 하나의 `assert`로 대체해서는 안 된다.

리팩터링 중 `velocity`를 먼저 갱신하고 이를 `position` 계산에 사용하면 명시적 오일러에서 반암시적 오일러로 **수치 방법 자체가 바뀐다**. 이는 코드 배치의 단순한 수정이 아니다. 나중에 같은 문제를 함수와 객체로 발전시킬 때에도 과학적 계산 의미를 유지하는 회귀 검증이 필요하다.

이번 P1은 계산 흐름과 상태 갱신을 이해하기 위한 예제이다. Chapter 4에서는 독립적인 계산 함수, Chapter 5에서는 상태 변경을 줄이는 방식, Chapter 6에서는 객체 상태, Chapter 9에서는 계약과 검증, Chapter 12에서는 다수 입자에 대한 배열 연산으로 연결할 수 있다. 책의 최종 통합 사례는 더 풍부한 동역학을 갖는 P2 조화진동자이다.

### Chapter 3 정리와 다음 장

절차적 프로그램의 품질은 단순히 명령문의 길이나 실행 성공 여부로 결정되지 않는다. **모델의 가정, 상태 변경, 계산 순서, 중간 결과, 종료 조건, 검증 기준이 명확한가**가 중요하다. 이 기반을 갖추면 Chapter 4에서 같은 계산을 독립적인 함수로 분리할 때 무엇을 경계로 나눌지 판단할 수 있다. 이는 절차적 프로그래밍의 폐기가 아니라 검증 가능성과 재사용성을 높이는 다음 단계이다.
